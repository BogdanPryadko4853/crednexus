# Шаблонные пояснения

Прямой ML API и новые результаты worker содержат русскоязычный блок `explanation`.
Он строится из численных результатов и причин решения, без LLM, ключей и внешних API.
Шаблоны не меняют предсказания, условия продукта или статус решения.

## Контракт

```json
{
  "template_version": "ru-templates-v1",
  "language": "ru",
  "title": "Прогноз кассового разрыва",
  "summary": "Краткое объяснение результата",
  "facts": ["Факты и суммы, использованные в пояснении"],
  "next_steps": ["Следующие действия"],
  "limitations": ["Границы применимости расчёта"]
}
```

| Где находится блок | Что объясняет |
|---|---|
| `POST /v1/score` → `explanation` | Две вероятности кредитных исходов и их смысл |
| `POST /v1/forecast` → `explanation` | Прогнозируемые месяцы и направления операционного потока |
| `forecasts[i].explanation` | Поступления, выплаты и интервалы конкретного месяца |
| `POST /v1/cash-gap` → `explanation` | Первый дефицит, потребность в пополнении, резерв, неблагоприятный сценарий и плановые движения |
| Решение backend → `explanation` | Фактические причины одобрения, отказа, контрпредложения или рассмотрения сотрудником |

Для асинхронных заданий пояснения возвращаются в `JobView.result` вместе с исходным
результатом. При оценке заявки блоки находятся в `result.score.explanation` и
`result.decision.explanation`. Последнее решение также доступно через
`GET /api/v1/applications/{id}/decision`.

Worker сохраняет пояснения вместе с результатами в JSONB. Изменений схемы БД не нужно.
Старые записи автоматически не пересчитываются; для старого типизированного ответа
без пояснения допустимо `explanation: null`, а в ранее сохранённом `JobView.result`
поле может отсутствовать. Клиент должен учитывать оба варианта.

## Смысл текстов

- Пояснение скоринга сообщает оценённые вероятности, не выдумывает причины прогноза
  и не присваивает категории риска без правил продукта.
- Причины кредитного решения соответствуют уже сработавшим правилам. Текст может
  содержать запрошенную сумму, лимит, срок, возраст бизнеса и пороги риска.
- При контрпредложении указаны запрошенная и предложенная суммы; принятие условий
  требует новой оценки риска. Одобрение не обещает фактическую выдачу денег.
- Отрицательный операционный поток в прогнозе не объявляется кассовым разрывом:
  для него требуется расчёт остатка и учёт плана.
- При кассовом разрыве различаются нехватка в первом проблемном месяце и максимальная
  сумма пополнения за весь прогноз. Например, дефициты 100, 200 и 300 означают
  необходимое пополнение 300, а не 600.
- Запас денег ниже резерва и отрицательный остаток объясняются отдельно.
- Плановые инвестиции и кредитные платежи перечисляются как учтённые движения.
  Текст не утверждает, что конкретный платёж единолично вызвал дефицит.
- Неблагоприятный сценарий не называется вероятностью разрыва или гарантированным
  интервалом остатка. Сохраняется ограничение проверки остатков только на конец месяца.

Суммы форматируются в рублях, с пробелами между разрядами и запятой перед копейками.
Очень маленькие ненулевые суммы не превращаются в текстовый ноль. Округление нужно
только для отображения: вычисления и правила используют исходные числовые значения.

Готовый текст для синтетического примера кассового разрыва:
[cash_gap_explanation.json](../examples/cash_gap_explanation.json).

## Проверки без запуска backend и PostgreSQL

Из `ml-service` с установленными тестовыми зависимостями:

```bash
python -m unittest discover -s tests -v
python -m unittest discover -s backend_tests -p test_explanations.py -v
python -m unittest discover -s backend_tests -p test_policy.py -v
```

Проверяются численные основания текстов, четыре вида кредитного решения,
различие первого и максимального дефицита, резерв, отрицательный операционный поток,
календарный порядок выбранных месяцев, совместимость старых ответов, HTTP-ответы
прямого ML API и сериализация результата worker без подключения к БД.

# HTTP API ML-сервиса v1

Сервис получает наблюдения и параметры заявки, собирает признаки и выполняет четыре
готовые ONNX-модели на CPU. Обучение, большой датасет и доступ к внешним API не нужны.
Сервис не принимает кредитное решение: правила одобрения остаются в backend.

[Интеграция с Java backend](JAVA_INTEGRATION.md): источники данных, клиент, ошибки и workflow.
Снимок контракта: [openapi-ml.json](openapi-ml.json).

## Запуск

Из `ml-service`, Python 3.13:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-api.txt
python -m uvicorn crednexus_ml.api:app --host 127.0.0.1 --port 8000
```

Swagger UI: http://127.0.0.1:8000/docs. OpenAPI: http://127.0.0.1:8000/openapi.json.
Схемы запросов и ответов генерируются из Pydantic-моделей.

Необязательные переменные окружения:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `CREDNEXUS_MODELS_DIR` | `ml-service/models/onnx` относительно кода | Каталог комплекта моделей; не зависит от текущего рабочего каталога |
| `CREDNEXUS_MODEL_THREADS` | `4` | Потоки ONNX Runtime на модель, целое от 1 до 64 |
| `CREDNEXUS_DEVICE` | `auto` | Диагностика устройства и CPU fallback; [подробности](CI.md) |

На старте каждого процесса загружаются четыре модели, проверяются SHA256 артефактов
и выполняется прогрев с проверкой эталонных прогнозов и интервалов. Ошибка загрузки
останавливает запуск. Запросы используют уже загруженные сессии. Каждый дополнительный
Uvicorn worker создаёт собственный комплект сессий.

API предназначен для внутреннего вызова backend. Аутентификация и ограничение доступа
в этой версии не реализованы.

## Методы

| Метод | Назначение |
|---|---|
| `GET /health/live` | Процесс отвечает |
| `GET /health/ready` | Модели загружены и прогреты; иначе 503 |
| `POST /v1/score` | Вероятности двух кредитных исходов на следующие 12 месяцев |
| `POST /v1/forecast` | Поступления, операционные выплаты и их разность для горизонтов 1–3 месяца |
| `POST /v1/cash-gap` | Остатки денег, первый месяц дефицита и потребность в пополнении с учётом плановых движений |

Контракт, формулы и пример расчёта кассового разрыва: [CASH_GAP.md](CASH_GAP.md).
Ответы также содержат [русскоязычные шаблонные пояснения](EXPLANATIONS.md)
в поле `explanation`; в прогнозе поясняется и каждый месяц.

Готовые синтетические запросы:

```bash
curl --fail-with-body http://127.0.0.1:8000/health/ready
curl --fail-with-body http://127.0.0.1:8000/v1/score \
  -H 'Content-Type: application/json' --data-binary @examples/score_request.json
curl --fail-with-body http://127.0.0.1:8000/v1/forecast \
  -H 'Content-Type: application/json' --data-binary @examples/forecast_request.json
```

## Общий контракт

- Все суммы — рубли, без масштабирования в тысячи/миллионы; значения от 0 до `1e15`.
  Для положительных суммы заявки и лимита ноль запрещён. JSON-числа обязательны:
  строки, boolean, NaN и Infinity не принимаются.
- `as_of_month` — последний закрытый месяц, дата строго `YYYY-MM-01`.
  Например, `2026-09-01` означает данные после закрытия сентября.
  Backend отвечает за то, что месяц действительно закрыт. Исторические и сценарные
  даты разрешены; сервис не подменяет их текущей датой.
- `company.sector` — отрасль; известные категории перечислены в `schema.json`.
  Неизвестная непустая категория допускается, кодируется `-1` и даёт предупреждение.
- `company.business_age_months` — возраст на конец месяца среза, целое от 3 до 1200.
- `history` — 3–120 записей с уникальными месяцами. Порядок записей произвольный.
  Каждая содержит `month` и все пять полей: `sales`, `cash_inflow`,
  `operating_cash_outflow`, `cash_balance`, `operating_expense`.
  `null` означает неизвестное значение; `0` означает известный ноль.
- Обязательны записи за каждый из последних трёх месяцев, включая месяц среза.
  Для каждого показателя нужно хотя бы одно известное значение в этом окне.
  Будущие месяцы и наблюдения до рождения компании отклоняются.
  Более ранние пропущенные месяцы сохраняются как NaN; интерполяции нет.
- Используются последние 13 календарных месяцев: они нужны для лага 12 и YoY.
  Более старая история не влияет на прогноз.
- Неизвестные поля отклоняются на всех уровнях, в том числе labels и готовые
  модельные признаки: клиент передаёт наблюдения, а не произвольную матрицу модели.

`sales` и `operating_expense` — начисленные продажи и операционные расходы;
`cash_inflow` и `operating_cash_outflow` — фактические поступления от покупателей
и операционные выплаты. Кредиты, обслуживание долга, инвестиции и взносы владельца
не входят в эти потоки. `cash_balance` — остаток на конец месяца.

## Дополнительные поля скоринга и источники

| Блок | Поля / единицы | Источник в MVP |
|---|---|---|
| `company` | `sector`, возраст в месяцах | Карточка синтетической компании |
| `history` | Пять ежемесячных показателей | Имитируемые бухгалтерия и банковская выписка |
| `application` | `requested_amount`, `term_months`, `annual_rate`, `purpose`, `product_limit` | Заявка и каталог продуктов backend |
| `financial_snapshot` | Дебиторка, кредиторка, просроченная кредиторка, долг, просроченный долг, запасы | Имитируемые бухгалтерия и кредитные данные |
| `financial_snapshot` | Правовая форма, концентрации покупателей/канала, состояние бизнеса | Карточка и финансовый срез компании |
| `financial_snapshot.existing_monthly_debt_service` | Плановый месячный платёж по существующим долгам | Имитируемый платёжный график |
| `bureau_history` | 12 месячных значений `dpd`, включая месяц среза | Имитируемый БКИ |

Адаптер backend должен сформировать эти блоки. Сам HTTP-сервис не запрашивает
БКИ/бухгалтерию и не восстанавливает неизвестную задолженность из оборота.
Демонстрационные значения заданы в `examples/score_request.json`.

`annual_rate` — годовая ставка долей единицы: `0.18`, а не `18`.
Допустимы 0–1; `term_months` — целое 1–1200. Для расчёта платежа сохранён
обучающий минимум ставки `0.001`: при ставке ниже него возвращается `RATE_FLOOR`.
Лимит продукта не является валидатором одобрения: превышение лимита обрабатывает backend.

`financial_snapshot.month` должен совпадать с месяцем среза. Обязательные поля:

- `legal_form` (`IP` / `OOO`; неизвестное значение допускается с предупреждением);
- `largest_customer_share`, `largest_channel_share` — доли 0–1;
- `accounts_receivable`, `accounts_payable`, `overdue_payables`, `debt_outstanding`,
  `loan_arrears`, `inventory`, `existing_monthly_debt_service` — неотрицательные суммы;
- `business_state` — `active`, `distressed` или `restructuring`.

Просроченная кредиторка не может превышать общую кредиторку. Закрытые и ещё
не начавшие деятельность компании не входят в контракт скоринга.
Поля снимка обязательны, не заменяются нулями при отсутствии данных.

`bureau_history` содержит ровно последние 12 уникальных последовательных месяцев.
Каждая запись: `month`, `dpd` — целое число дней просрочки 0–100000. Нулевой DPD
должен означать подтверждённое отсутствие просрочки, включая месяцы без кредитов.
Недоступную историю нельзя выдавать за нулевую: backend должен запросить сведения.
Текущий DPD, максимум и число месяцев с просрочкой сервис вычисляет сам.

## Прогноз

Кроме общего контракта, принимается `horizons`: непустой список уникальных целых
1–3, по умолчанию `[1, 2, 3]`. Ответ сохраняет порядок этого списка.
Месяцы цели рассчитываются календарно, включая переход года.

Для каждого месяца ответ содержит `cash_inflow`, `operating_cash_outflow`
с полями `lower`, `prediction`, `upper`, а также `operating_net_cash_flow`:
разность двух точечных прогнозов. Это не прогноз остатка на счёте.
Интервалы относятся к каждому потоку отдельно; интервал их разности не заявляется.
`interval_nominal_coverage=0.9` — номинальная цель калибровки, не гарантия покрытия
при дрейфе. По сохранённому stress-test фактическое покрытие ниже 90%.

## Признаки и воспроизводимость

`crednexus_ml.history.history_features` используется и генератором обучающих данных,
и онлайн-сборкой. Окна включают месяц среза; стандартное отклонение имеет `ddof=0`.
Средние считают только известные значения. Доля пропусков в 12 месяцах включает
отсутствующие месяцы. YoY отсутствует, если нет текущего или положительного прошлогоднего
значения. Для cashflow сохраняется обучающее приведение исторических агрегатов к float32.
Сезонное значение берётся из фактически наблюдённого месяца «цель минус 12».
Финансовые отношения и кодирование категорий выполняет существующий загрузчик модели.

`model_version` — полный SHA256 файла контрольных сумм комплекта,
`feature_version=monthly-v1` — версия сборки признаков. Версия HTTP API — v1.
Перенос функции не меняет веса или расчёт агрегатов; новые manifests генератора
также фиксируют SHA256 общего `history.py`. Сохранённые старые manifests и provenance
моделей не переписываются. Строгий validator старого датасета с новой версией исходников
отклонит несовпавший fingerprint; для повторного аудита используйте исходный commit
генератора либо новый набор в отдельном каталоге.

## Ошибки и предупреждения

Ошибки структуры, значений и истории возвращают HTTP 422:

```json
{
  "code": "VALIDATION_ERROR",
  "errors": [{"location": ["body", "history", 0, "sales"], "type": "greater_than_equal", "message": "Input should be greater than or equal to 0"}]
}
```

Исходные финансовые значения в ошибку не включаются. Неожиданная ошибка выполнения
даёт HTTP 500 с `code=INFERENCE_ERROR`; отсутствие загруженных моделей — 503.

Успешный ответ содержит `warnings`:

- `SYNTHETIC_MODEL` — всегда: модели обучены на сценарной синтетике;
- `INCOMPLETE_HISTORY` — неполные 13 месяцев или пропуски в наблюдениях;
- `SHORT_HISTORY` — возраст компании менее 12 месяцев;
- `UNKNOWN_CATEGORY` — категория отсутствует в обучающем словаре;
- `RATE_FLOOR` — применён обучающий минимум ставки.

## Проверки

```bash
python -m pip install -r requirements-test.txt
python -m unittest discover -s tests -v
```

Тесты сравнивают собранные признаки с исходными строками симулятора по схемам ONNX,
проверяют реальные модели через HTTP, даты, ошибки, пропуски, повторное использование
сессий и отказ запуска с повреждёнными артефактами. Жизненный цикл моделей использует
[FastAPI lifespan](https://fastapi.tiangolo.com/advanced/events/).

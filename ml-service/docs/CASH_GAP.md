# Прогноз кассового разрыва

`POST /v1/cash-gap` рассчитывает остатки на конец ближайших 1–3 месяцев.
Поступления и операционные выплаты прогнозируют существующие ONNX-модели.
Обслуживание долга и прочие плановые движения задаёт вызывающая сторона.
Дополнительное обучение и новые зависимости не нужны.

## Запрос

Общие поля `as_of_month`, `company`, `history` соответствуют [контракту API](API.md).
Начальный остаток берётся из `cash_balance` истории за `as_of_month`: значение
обязательно должно быть известно. Отдельного переопределения остатка нет.

Дополнительные поля:

| Поле | Смысл |
|---|---|
| `months` | Целое 1–3, по умолчанию 3; прогноз всегда начинается со следующего месяца и идёт без разрывов |
| `minimum_cash_reserve` | Желаемый минимальный остаток в рублях; по умолчанию 0 |
| `cash_plan` | По одной записи на каждый прогнозный месяц, порядок произвольный |

В каждой записи `cash_plan` обязательны `month` и пять неотрицательных сумм:

- `debt_service` — выплаты основного долга, процентов и кредитных комиссий;
- `investments` — инвестиционные выплаты, например приобретение оборудования;
- `financing_inflow` — поступления займов или взносов собственника;
- `other_inflow` — прочие поступления, не вошедшие в модельный операционный поток;
- `other_outflow` — прочие выплаты, не вошедшие в модельный операционный поток.

Если движения нет, передайте явный `0`. Отсутствующее значение не означает ноль.
Если план неизвестен, нужно получить его у пользователя или источника данных.
Не включайте сюда повторно поступления покупателей и обычные операционные выплаты:
они уже учтены моделями. Запланированное финансирование — предположение сценария,
а не подтверждение одобрения или выдачи кредита.

Пример записи плана:

```json
{
  "month": "2026-10-01",
  "debt_service": 120000,
  "investments": 2000000,
  "financing_inflow": 0,
  "other_inflow": 0,
  "other_outflow": 0
}
```

Полный синтетический пример: [cash_gap_request.json](../examples/cash_gap_request.json).
Для работающего сервиса:

```bash
curl --fail-with-body http://127.0.0.1:8000/v1/cash-gap \
  -H 'Content-Type: application/json' --data-binary @examples/cash_gap_request.json
```

## Расчёт

```text
Остаток на конец месяца = остаток на начало
  + прогноз поступлений − прогноз операционных выплат
  + financing_inflow + other_inflow
  − debt_service − investments − other_outflow
```

Конечный остаток переносится в следующий месяц, включая отрицательные значения.
Неявного пополнения, обнуления дефицита или автоматического кредита нет.
Плановые движения изменяют только расчёт остатка: модели операционных потоков
не моделируют эффект будущего финансирования или инвестиций на развитие бизнеса.
Десятичная арифметика предотвращает появление ложного разрыва из-за ошибок суммирования
float. API возвращает JSON-числа, без принудительного округления до рублей/копеек.

В ответе два сценария:

- `base`: точечные прогнозы поступлений и выплат;
- `adverse`: нижние границы прогнозов поступлений и верхние границы выплат,
  при тех же начальном остатке и плане.

`adverse` — неблагоприятный сценарий. Он не является 90%-интервалом остатка,
оценкой вероятности кассового разрыва или гарантированным худшим исходом:
интервалы исходных потоков калиброваны отдельно.

## Ответ

Общие поля: `model_version`, `feature_version`, `calculation_version=cash-gap-v1`,
`warnings`, месяц среза, начальный остаток, минимальный резерв и отсортированный план.
Поле `explanation` содержит [шаблонное пояснение](EXPLANATIONS.md) на русском языке.
В каждом сценарии:

| Поле | Смысл |
|---|---|
| `first_cash_gap_month` | Первый месяц с отрицательным конечным остатком; иначе `null` |
| `first_reserve_breach_month` | Первый месяц с остатком ниже резерва; может быть месяцем среза, если начальный остаток уже ниже резерва |
| `minimum_balance` | Минимум начального остатка и всех прогнозных конечных остатков |
| `funding_to_avoid_cash_gap` | `max(0, -minimum_balance)` |
| `funding_to_maintain_reserve` | `max(0, minimum_cash_reserve - minimum_balance)` |
| `months` | По месяцам: начальный/конечный остатки, прогнозные потоки, суммы прочих движений, чистый поток и дефициты |

Размер пополнения — минимальная дополнительная сумма, доступная **до начала
прогноза**, при неизменном плане. Она не добавлена в показанные остатки. Это
максимальный накопленный дефицит, а не сумма дефицитов всех месяцев.
Пополнение для поддержания резерва уже включает покрытие отрицательного остатка;
эти две суммы не нужно складывать.

Например, начальный остаток 100 и конечные остатки −45, 55, 45 означают
потребность в пополнении 45 для исключения отрицательного остатка. При резерве
20 потребность составляет 65. Возврат к положительному остатку во втором месяце
не отменяет разрыва в первом.

Нулевой остаток не считается кассовым разрывом. Остаток, равный резерву,
не считается нарушением резерва. `cash_shortfall` и `reserve_shortfall`
в месячных строках относятся к соответствующему конечному остатку.

## Границы и проверки

Прогноз показывает остатки **на конец месяца**. Он не обнаруживает временную нехватку
денег внутри месяца: для этого нужны дневные потоки и календарь платежей.
Предупреждения `MONTHLY_RESOLUTION`, `ADVERSE_SCENARIO` и предупреждение о
синтетических моделях присутствуют в каждом успешном ответе.

Ошибки возвращают HTTP 422: отсутствующий текущий остаток, неполный/дублирующийся план,
план за прошлый или лишний месяц, отрицательные суммы, неизвестные поля и неверные типы.
Остальные ограничения истории наследуются от общего контракта.

Тесты покрывают накопление дефицита, восстановление остатка, учёт каждой категории
плана, нулевую границу, дробные суммы, резерв, переход года, порядок плана,
проверки входов и выполнение через HTTP с реальными ONNX-моделями.

# CredNexus — ML и кредитный backend

Реализованы FastAPI backend, асинхронный PostgreSQL, очередь ML-заданий с отдельным
worker, скоринг, прогноз потоков и кассового разрыва, заявки и демонстрационные
кредитные правила. Демонстрационные данные синтетические.
Java backend, Keycloak, MinIO и frontend развиваются отдельно; интеграция Java с HTTP ML пока не подключена.

```bash
cp .env.example .env
docker compose -f compose.python.yaml up --build -d
```

Swagger backend: http://127.0.0.1:8000/docs. Для `/api/v1/*` нужен заголовок
`X-API-Key` со значением `CREDNEXUS_BACKEND_API_KEY` из `.env`.

- [Запуск backend, API, бизнес-правила и тесты](ml-service/docs/BACKEND.md)
- [Интеграция с Java: контракты, клиент, workflow и недостающие данные](ml-service/docs/JAVA_INTEGRATION.md)
- [Прямой ML API без PostgreSQL](ml-service/docs/API.md)
- [Расчёт кассового разрыва](ml-service/docs/CASH_GAP.md)
- [Модели и метрики](ml-service/docs/DEPLOYMENT.md)
- [CI, Docker, healthcheck и запуск без GPU](ml-service/docs/CI.md)

Сквозная проверка из `ml-service` после запуска Compose:

```bash
export CREDNEXUS_BACKEND_API_KEY=synthetic-local-demo-api-key
python scripts/backend_demo.py
```

Если ключ изменён, используйте своё значение. Java backend в `backend/` запускается
через корневой `compose.yaml`; его скоринг сейчас работает по правилам. Команда выше
запускает отдельный Python-контур. Ниже сохранено исходное ТЗ хакатона.

# Альфа-Хак — Умный кредитный кабинет предпринимателя

> **Сжатое ТЗ по кейсу Альфа-Банка (16 страниц).** Документ сохраняет обязательные требования, нюансы сценария и критерии проверки, убирая вводные и повторения. Это **конспект задания, а не описание уже реализованного проекта**.

## 1. Цель и пользователи

Создать **работающий прототип цифрового кредитного конвейера для малого и микробизнеса**, объединяющий:

- **Клиентскую часть:** от потребности в финансировании, выбора продукта и заполнения заявки до получения понятного результата.
- **Банковскую часть:** прием и проверку данных, их обогащение (в том числе смоделированное), оценку риска и кредитное решение.
- **Единый процесс:** данные сохраняются между этапами, действия меняют состояние заявки, статус и следующие шаги отображаются динамически.

**Пользователи:** собственник, генеральный директор, финансовый директор/бухгалтер или иной уполномоченный сотрудник компании. Нельзя предполагать, что клиент разбирается в банковских процессах: интерфейс должен объяснять варианты, статусы и дальнейшие действия.

## 2. Что необходимо реализовать

1. **Исследовать и описать сценарий:** потребности клиента и банка, границы MVP, этапы, роли, данные, события и возможные исходы.
2. **Веб-кабинет клиента:** выбор подходящего кредитного продукта, ввод сведений о компании и параметров финансирования, создание и отправка заявки, просмотр статуса и результата, выполнение необходимых действий внутри системы.
3. **Обработку на стороне банка:** получение заявки, валидацию полноты и корректности, запрос/уточнение недостающих данных, проверки, оценку риска, принятие решения (автоматически или с участием сотрудника — согласно выбранному MVP).
4. **Согласованную сквозную бизнес-логику:** реальные переходы состояний, сохранение и переиспользование введенных данных, реакцию на пользовательские действия, прозрачный прогресс заявки.
5. **Демонстрационный end-to-end сценарий:** эксперт самостоятельно проходит путь от запроса на кредит до результата на работающем прототипе.

**Важно:** организаторы не требуют воспроизводить весь настоящий банковский конвейер. Допустим ограниченный **реалистичный MVP**, но выбранные этапы, роли, проверки и упрощения нужно обосновать. Набор отдельных экранов без работающего процесса не подходит.

## 3. Минимальная предметная логика

### Кредитный путь

```text
Потребность бизнеса
  → Выбор кредитного продукта
  → Заявка (цель, сумма, срок, сведения о бизнесе)
  → Отправка и регистрация
  → Проверка полноты и корректности
  → При необходимости: уточнение/дозаполнение
  → Обогащение данными и проверки (допускаются симуляторы)
  → Скоринговая оценка риска
  → Кредитная логика и решение
  → Отображение результата и следующих шагов
  → При положительном результате: оформление/выдача (могут быть симулированы)
```

**Возможные источники данных (примеры, не обязательные реальные интеграции):** бюро кредитных историй, ЕГРЮЛ/ЕГРИП, ФНС «Прозрачный бизнес», внутренние системы. В автономной демоверсии использовать моки/стабы/симуляторы.

### Скоринг ≠ кредитное решение

- **Скоринг** оценивает риск по факторам: доходы/расходы, финансовые показатели, долги, просрочки, платежная дисциплина, параметры заявки и т. п.
- **Итоговое решение** также зависит от условий конкретного продукта, суммы, срока, внешних проверок и правил банка. Один риск-балл не обязан означать одинаковый результат для разных продуктов.
- Сложное ML **не обязательно**. Допустимы прозрачные правила, баллы, статистические модели и комбинация автоматики с экспертной оценкой.
- Исход не обязан быть бинарным: **одобрение, отказ, запрос дополнительных сведений или предложение измененных условий** (иная сумма/срок/продукт). Логика должна объяснять, почему и что делать дальше.

**Практический пример состояний для MVP (предложение, не обязательный перечень из кейса):** `DRAFT → SUBMITTED → VALIDATING → NEEDS_INFO / UNDER_REVIEW → APPROVED / COUNTER_OFFER / REJECTED`. Определить допустимые переходы и действия каждой роли.

## 4. Строгие ограничения

| Область | Требование |
|---|---|
| Интерфейс | Клиентская часть **только веб**; мобильное приложение вместо нее не допускается. |
| Весь основной путь | Проходит **внутри продукта**: email, SMS, звонки и мессенджеры не могут быть обязательными шагами. |
| Автономность | **Без доступа к корпоративным системам Альфа-Банка**; необходимые интеграции имитируются локально. |
| Данные | Только **синтетические** сведения о клиентах, организациях, сотрудниках, документах, заявках и финансах. |
| Стоимость | Проверяемая версия **не зависит от платных API/подписок, покупных данных и закрытых корпоративных лицензий**. Инструменты, использованные только в разработке, под это ограничение не подпадают. |
| LLM | Если применяются, разрешены **только модели с открытыми весами**. ИИ вообще не обязателен. |
| Упрощения | Можно упрощать кредитную логику, подписание и фактическую выдачу денег, а также контракты внешних сервисов. **Все допущения явно описать**, не разрушая связность процесса. |
| Развертывание | Решение должно быть **cloud-native, запускаться в Docker** и воспроизводимо подниматься со всеми компонентами на обычном ПК. |

## 6. Критерии успеха

1. **Целостность:** от обращения за финансированием до результата — единый работающий путь.
2. **Проверяемость:** эксперт может запустить продукт и пройти сценарий с предоставленными данными.
3. **UX:** понятный процесс для клиента и банковских ролей, очевидные действия и статусы.
4. **Согласованность модулей:** данные не теряются, состояния изменяются последовательно.
5. **Enterprise-подход:** безопасность, надежность, отказоустойчивость, масштабируемость, управляемые зависимости и сопровождение — на уровне разумной архитектуры и объяснения решений.
6. **Потенциал развития:** команда объясняет компромиссы, ограничения и следующий этап развития.

**Дополнительные функции** (LLM-ассистент, OCR, автоматизация и т. п.) приветствуются **лишь когда улучшают сценарий, а не подменяют рабочее ядро**.

## 7. Рекомендации по приоритетам реализации

**Порядок для MVP (практическая интерпретация кейса):**

1. Сначала описать 1–2 реальные потребности бизнеса, роли, шаги и границы процесса — **не начинать только с макетов**.
2. Зафиксировать модель данных, статусы заявки и правила переходов.
3. Реализовать связку **веб-кабинет → сервер → хранилище → обработка → решение → обновление интерфейса**.
4. Добавить синтетические данные, воспроизводимые проверки и при необходимости банковский интерфейс.
5. Подготовить Docker-запуск, документацию, тестовый сценарий и артефакты сдачи.
6. Только после этого добавлять ИИ, распознавание документов, расширения и внешнюю демоверсию.

Методы CustDev, JTBD, user story mapping, RICE/ICE/MoSCoW **не обязательны**; использовать их стоит только для обоснованных продуктовых решений.

## 8. Короткая проверка перед сдачей

**Контрольный вопрос:** сможет ли эксперт, имея только репозиторий и README, **локально запустить систему, зайти с синтетическими данными, подать заявку, увидеть проверки/движение статусов и получить объяснимый результат** — без платных сервисов, корпоративного доступа, SMS или личных объяснений команды?

Если да, а в репозитории также есть все файлы из раздела 5, базовая цель задания выполнена.
